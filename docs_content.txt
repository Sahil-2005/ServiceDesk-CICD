This SRS builds directly upon the Week 1 Problem Definition and Scope document and the Week 2 Agile Planning and DevOps Workflow document. It does not redefine project scope; it formalises the MVP, user stories, and acceptance criteria already established into a structured requirements specification, prior to the start of implementation.
1. Introduction
1.1 Purpose
The purpose of this document is to specify, in a structured and verifiable form, what the IT Service Desk Portal must do. It defines the system's functional and non-functional requirements, business rules, data requirements, and interface expectations, so that development (beginning in the weeks following this document) proceeds against a shared, unambiguous definition of the required behaviour. This SRS describes WHAT the system must do; it deliberately does not describe HOW the system will be built — detailed software architecture, database schema design, and deployment/infrastructure architecture are addressed in separate documents later in the project.
1.2 Scope
This SRS covers the IT Service Desk Portal application only — the ticket-management web application used by Employees, IT Support Staff, and Administrators. It does not specify requirements for the DevOps/CI-CD pipeline (Git/GitHub workflow, Jenkins pipeline stages, Selenium test design, Docker image structure, or Ansible/Puppet configuration); those remain governed by the DevOps workflow defined in the Week 2 document and will be elaborated in their own technical design documents. The application requirements documented here are limited to the MVP feature set established in Week 1: ticket creation, viewing, updating, and searching; a role-based ticket status workflow; and a summary dashboard.
1.3 Intended Audience
The project team (developers, tester, DevOps-responsible member, database/API-responsible member, project coordinator), as the primary implementers of this specification.
The project guide/faculty, for evaluation of requirement completeness, clarity, and testability.
Any future reader of the project documentation seeking to understand what the IT Service Desk Portal is required to do, independent of how it was implemented.

2. Overall Description
2.1 Product Perspective
The IT Service Desk Portal is a new, standalone web application; it does not replace or integrate with any existing enterprise ticketing system. It is developed as the application component of a larger academic project whose primary learning objective is the surrounding CI/CD pipeline. The portal is self-contained: it manages its own users, tickets, and categories, and does not depend on external systems such as Active Directory, email servers, or third-party helpdesk platforms.
2.2 Product Functions
At a high level, the system provides the following functions, each elaborated into detailed functional requirements in Section 3:
User authentication and role-based access control.
Creation, viewing, updating, and searching of IT support tickets.
A defined ticket status workflow with role-restricted transitions.
A summary dashboard presenting aggregated ticket metrics.
Administrative management of user accounts.
2.3 User Classes
User Class
Description
Technical Expertise Expected
Employee
General staff member who raises tickets for IT issues encountered during their work and tracks their own tickets.
Basic computer literacy; no technical/IT background assumed.
IT Support Staff
Handles the ticket queue: investigates, updates status, and resolves tickets raised by Employees.
Working technical familiarity with common IT issues; comfortable with web applications.
Administrator
Oversees the system: manages user accounts, has full ticket visibility, and monitors the dashboard.
Highest familiarity with the system as a whole; may also perform IT Support Staff duties.
2.4 Operating Environment
The system is a web application accessed through a standard desktop or laptop web browser; no native mobile application is in scope (as per the Week 1 out-of-scope list).
The application is expected to run on a single server/virtual machine environment suitable for an academic deployment, and — from the relevant project week onward — inside a Docker container as defined by the DevOps workflow.
The exact runtime platform, programming language, and framework are implementation decisions to be finalised in the technical design phase and are outside the scope of this document.
2.5 Constraints
The system must be implementable by a small student team within the remaining academic weeks of a 15-week project.
Only free or open-source technologies may be used, consistent with the Week 1 resource constraint.
The application must be compatible with containerisation via Docker and automated testing via Selenium, since both are required later in the project timeline.
2.6 Assumptions
A single hypothetical organisation is assumed as the operating context, consistent with the Week 1 assumptions; the system is not being built for a real, live organisation.
Users are provisioned with accounts by an Administrator; self-registration by Employees is not assumed to be in scope unless specified otherwise in a later design document.
Network connectivity between users and the hosted application is assumed to be available and is not itself a system requirement.
2.7 Dependencies
The application's testability depends on the automated Selenium test cases planned in the Week 2 backlog (PB-10), which in turn depend on the functional requirements in this document being stable before test scripts are written.
The application's deployment depends on the Docker and Ansible/Puppet work planned for later weeks (PB-11–PB-13); this SRS assumes that dependency but does not specify it further.
3. Functional Requirements
Each functional requirement below is assigned a unique ID and written to be independently testable. Requirements are grouped by feature area, consistent with the MVP defined in Week 1.
3.1 Authentication

Description

FR-02
Logout
The system shall allow a logged-in user to log out, terminating their active session so that further access requires re-authentication.
FR-03
Role-Based Access
The system shall determine, at login, the user's role (Employee, IT Support Staff, or Administrator) and shall restrict visible features and data to those permitted for that role, as defined in Section 6 (Business Rules).
3.2 Ticket Management
ID
Requirement
Description
FR-04
Create Ticket
The system shall allow a logged-in Employee to create a new ticket by supplying, at minimum, a title, description, and category. The system shall generate a unique ticket ID and set the initial status to "Open" automatically upon creation.
FR-05
View Ticket
The system shall allow a user to view a list of tickets scoped to their role (Employee: own tickets; IT Support Staff: the shared/assigned queue; Administrator: all tickets) and to open an individual ticket to view its full detail, including status history and resolution notes.
FR-06
Update Ticket
The system shall allow IT Support Staff and Administrators to update a ticket's status (per the workflow in Section 3.3) and to add resolution notes. The system shall record the date and time of each update.
FR-07
Search Ticket
The system shall allow a user to search or filter the ticket list visible to their role by keyword (matching title/description), status, and category, returning matching results without requiring an exact match on the full title.
3.3 Ticket Workflow
The ticket status lifecycle is refined at this stage to include an explicit "Assigned" state between "Open" and "In Progress," so that ticket ownership is unambiguous before work begins. This refinement adds clarity within the workflow already introduced in Week 1/Week 2 and does not alter the MVP scope. The defined lifecycle is:
Open → Assigned → In Progress → Resolved → Closed
State
Meaning
Open
The ticket has been created by an Employee and has not yet been assigned to an IT Support Staff member.
Assigned
The ticket has been taken up by (or assigned to) a specific IT Support Staff member, but work has not yet actively started.
In Progress
The assigned IT Support Staff member is actively working on the ticket.
Resolved
The IT Support Staff member has completed the required work and recorded resolution notes; the ticket awaits closure.
Closed
The ticket is confirmed complete and requires no further action.

5. User Requirements
This section restates the system's requirements from each user role's own point of view, in plain language, complementing the formal functional requirements in Section 3.
5.1 Employee Perspective
I need to log in securely and see only my own tickets.
I need to report an IT issue quickly, without needing to know technical categorisation details beyond a simple category list.
I need to check the status of a ticket I previously raised without contacting IT support directly.
I need to find a specific past ticket without scrolling through my entire history.
5.2 IT Support Staff Perspective
I need a clear view of tickets that are open or assigned to me, so I know what requires attention.
I need to update a ticket's status and record what I did, so there is a record of my work.
I need to search or filter tickets by category to identify related or duplicate issues.
5.3 Administrator Perspective
I need full visibility of all tickets in the system, regardless of who raised or is handling them.
I need to manage user accounts so that access to the system is controlled.
I need a dashboard summary so that I can assess overall ticket volume and category trends without reviewing every ticket individually.
I need the ability to reassign a ticket when the original assignee cannot complete it.
6. Business Rules
BR — Required Ticket Fields
A ticket cannot be created without a title, a description, and a category; the system shall reject submission of a ticket missing any of these fields.
BR — Valid Status Transitions
A ticket may only move between statuses along the transitions defined in Section 3.3 (FR-08 to FR-12); any other transition is invalid and shall be rejected.
A ticket cannot be marked "Resolved" without accompanying resolution notes.
BR — Role Permissions
An Employee may create tickets and view/search only their own tickets; they may not update ticket status or view other Employees' tickets.
IT Support Staff may view, search, and update tickets in the shared/assigned queue; they may not manage user accounts.
An Administrator has all permissions available to IT Support Staff, plus user account management and the ability to reassign or close any ticket.
BR — Search Behaviour
Search shall match on partial text within the ticket title or description (not exact match only) and shall respect the same role-based visibility rules as ticket viewing — a user cannot search their way into seeing tickets they are not permitted to view.
Search results may be further narrowed by status and/or category filters, applied in combination with the keyword search.
7. External Interface Requirements
7.1 User Interface Requirements
The system shall provide a web-based graphical user interface accessible via a standard browser; no command-line interface is required.
The interface shall present role-appropriate navigation — an Employee shall not see menu items or controls for functions they are not permitted to use (e.g., user management).
Forms (such as ticket creation) shall provide visible validation feedback when a required field is missing or invalid.
7.2 API / Interface Expectations
The application is expected to expose an internal interface (e.g., a web API) between its user interface and its business logic/data layer, sufficient to support the functional requirements above and to allow the automated Selenium tests planned in the Week 2 backlog to exercise the application's workflows. The specific technology and API design are implementation decisions for the technical design phase and are not fixed by this SRS.
7.3 Database Interaction Expectations
The system is expected to persist ticket, user, and category data in a backing data store such that data survives an application restart. The specific database technology and schema are outside the scope of this document and will be addressed in a separate database design document; this SRS defines only the data content expected to be stored (see Section 8).
7.4 Browser Requirements
The application shall be usable on at least one current desktop browser (e.g., a recent version of Google Chrome or Mozilla Firefox).
The application is not required to support legacy browsers or to provide a dedicated mobile-optimised interface, consistent with the Week 1 out-of-scope decision on native mobile applications.

9. Security Requirements
ID
Requirement
SR-01
The system shall require a valid username and password before granting access to any ticket data or role-restricted function.
SR-02
Passwords shall be stored in a hashed (non-reversible) form rather than in plain text.
SR-03
The system shall enforce role-based access control server-side (not only by hiding UI elements), so that a user cannot access data or actions outside their role by directly requesting a restricted function.
SR-04
User sessions shall expire after a period of inactivity, requiring re-authentication.
SR-05
The system shall not expose one user's ticket data to another user who is not permitted to view it, as defined in Section 6.
10. Error Handling Requirements
ID
Requirement
ER-01
If a user submits a ticket creation form with a missing required field, the system shall reject the submission and clearly indicate which field(s) are missing, without discarding the data already entered.
ER-02
If a login attempt fails, the system shall display a generic error message that does not reveal whether the username or the password was incorrect, and shall not lock the interface itself (account lockout policy, if any, is a security decision to be defined in later design work).
ER-03
If a user attempts an action outside their role's permissions (e.g., an Employee attempting to update ticket status), the system shall reject the action and display an appropriate access-denied message.
ER-04
If an invalid status transition is attempted (Section 3.3), the system shall reject it and inform the user of the ticket's current valid next state(s).
ER-05
If the system is unable to persist a ticket creation or update (e.g., due to a backend/database error), the system shall inform the user that the action did not complete, rather than showing a false success confirmation.

1. System Overview
The IT Service Desk Portal is a role-based web application through which Employees raise IT support tickets, IT Support Staff work through and resolve those tickets, and an Administrator oversees users, categories, and overall ticket activity, exactly as specified in the SRS (Section 2, Product Perspective and Product Functions). This document defines the technical structure that will realise that specification: a browser-based frontend, a REST API backend, a relational database, and a surrounding DevOps/CI-CD pipeline that builds, tests, containerises, and deploys the application.
The system is designed as a single, self-contained web application (no integration with external directory services, email systems, or third-party helpdesk platforms — consistent with SRS Section 2.1) and is scoped for a small student team to design, build, and demonstrate over the remaining weeks of a 15-week academic project, using only free and open-source technologies (SRS Section 2.5).
1.1 Purpose of This Document
To translate the functional and non-functional requirements defined in the SRS into a concrete, implementable technical design: a chosen technology stack, an application architecture, a database schema at the conceptual level, an API contract, and a DevOps pipeline architecture (Git/GitHub, Jenkins, Selenium, Docker, and Ansible), so that development in subsequent weeks proceeds against a shared, unambiguous design rather than ad-hoc individual decisions.
1.2 Scope of This Document
Covers: application architecture, technology selection and justification, module decomposition, database conceptual design, REST API design, ticket lifecycle implementation, security architecture, deployment architecture, and CI/CD pipeline architecture.
Does not cover: functional requirements (defined in the SRS), sprint-by-sprint task allocation (defined in the Week 2 document), or actual source code, database DDL, or pipeline scripts — these are implementation artefacts produced in later weeks against this design.
1.3 Design Principles Followed
Traceability to the SRS: every module and data element maps to a named functional requirement (FR-xx) or data field from SRS Section 8.
Simplicity over sophistication: a small, coherent set of technologies that a 3–4 person student team can realistically learn, integrate, and operate within the remaining project weeks, in preference to a more “enterprise” but harder-to-manage stack.
Separation of concerns: presentation (frontend), business logic and API (backend), and persistence (database) are kept as distinct layers, and the DevOps pipeline is kept distinct from application logic.
Pipeline-readiness: every technology choice is deliberately compatible with Git/GitHub, Jenkins, Selenium, Docker, and Ansible, since these are mandated by the Week 1/2 project brief.

3. Technology Stack
The stack below is chosen to be coherent (few languages/runtimes to learn), free/open-source throughout, and directly compatible with the mandated DevOps tools and deployment target named in the official Week 1–15 task-allocation sheet for this project (Roll No. 24102B2003): a Maven/Gradle/Ant build tool and a Tomcat/Nginx deployment target, alongside GitHub, Jenkins, Selenium, Docker, and Ansible/Puppet. Wherever a simpler alternative would have served equally well within that constraint, the simpler option was preferred over a more “impressive” but harder-to-integrate one.
3.1 Frontend — React (with Vite) and plain CSS/Bootstrap
What: A single-page application (SPA) built with React, bundled using Vite, calling the backend over REST/JSON. Bootstrap (or plain CSS) is used for layout and form styling — no heavyweight design system is needed for an MVP UI.
Why: React is widely taught, well documented, and produces a static build (HTML/CSS/JS bundle) that is trivial to containerise and serve behind Nginx — the exact deployment target named in the task brief. It is built and packaged independently of the backend's Maven build, using its own lightweight npm/Vite toolchain, and the two are wired together only through the REST API contract (Section 10).
Fit with SRS: satisfies the web-based GUI requirement (§7.1), role-appropriate navigation, and client-side form validation feedback, while all authoritative validation and access control remain server-side (SR-03).
3.2 Backend — Java 17 with Spring Boot (REST API), built with Maven
What: A Java 17 backend built on the Spring Boot framework — Spring Web (MVC/REST controllers), Spring Data JPA (persistence over MySQL), and Spring Security (authentication and role-based authorization). The project is built, tested, and packaged as a deployable WAR using Apache Maven.
Why Java/Spring Boot + Maven: The department's official Week 1–15 task-allocation sheet for this project explicitly requires selecting “a Maven/Gradle/Ant build tool” (Week-3 task) and states that the Jenkins CI job is “a Maven/Gradle/Ant build job” (Week-7) whose Selenium suite is “executed locally through Maven” (Week-9). These three build tools are all part of the Java ecosystem, so the backend language follows from the mandated tooling rather than being chosen independently of it. Among the three, Maven is selected over Gradle and Ant (see Section 3.2.1). Spring Boot is, in turn, the most widely taught and best-documented Java web framework for building a REST API quickly, and it packages naturally as a WAR for deployment to Apache Tomcat — the deployment target the same brief names.
Fit with SRS: implements FR-01–FR-16 as Spring @RestController / @Service / @Repository classes; Spring Security enforces role-based access control server-side per SR-03, independent of what the UI displays.
3.2.1 Build Tool — Maven (preferred over Gradle and Ant)
Maven over Gradle: Maven's declarative XML POM (pom.xml) is more predictable and easier for a small student team to read and debug than Gradle's Groovy/Kotlin DSL build scripts, and Maven's “convention over configuration” project layout maps directly onto the WAR-packaging, Tomcat-deployment workflow the brief specifies, with less build-script authoring than Gradle typically requires.
Maven over Ant: Ant is a lower-level task runner with no built-in dependency management or standard project structure (both would need to be hand-rolled, e.g. with a separate Ivy configuration); Maven provides both out of the box, which materially reduces setup effort for a team new to Java build tooling.
Jenkins/Selenium fit: Maven has first-class Jenkins plugin support (build step, test-result publishing) and integrates the Selenium suite directly as Maven test/integration-test goals (mvn test / mvn verify), which is exactly how the brief's Week-9 and Week-10 tasks describe running and later automating the tests.
3.3 Database — MySQL
What: A relational database (MySQL, or MariaDB as a drop-in equivalent) holding Users, Tickets, Categories, and a ticket status-history table, accessed from the backend through Spring Data JPA (Hibernate) entities and repositories.
Why: The data described in SRS §8 is naturally relational — a ticket has a fixed set of fields, references a category and a creator/assignee (both Users), and requires reliable, atomic status updates. A relational database gives referential integrity (e.g., a ticket cannot reference a non-existent category) and straightforward reporting queries for the dashboard (COUNT/GROUP BY), which a document store would not provide as naturally. MySQL is free, mature, has first-class Docker images, and pairs directly with Spring Data JPA, keeping the learning curve low.
Fit with SRS: persists all fields in the SRS §8 data dictionary; supports FR-13/FR-14 dashboard aggregation via simple grouped queries; satisfies NFR-04 (no loss of confirmed data) through transactional writes (Spring's @Transactional).
3.4 API Technology — REST over HTTPS, JSON
What: A RESTful API (resource-oriented endpoints under /api/...), implemented as Spring MVC @RestController classes returning JSON, secured with token-based authentication (JSON Web Tokens, JWT) via Spring Security.
Why: REST is simple to design, simple for Selenium/integration tests to exercise independently of the UI, and requires no extra infrastructure (unlike, e.g., GraphQL or gRPC, which would add complexity disproportionate to the MVP's needs). Spring Web is the standard, well-documented way to expose REST endpoints from a Spring Boot application.
Fit with SRS: directly satisfies §7.2 (“an internal interface, e.g., a web API, sufficient to support the functional requirements ... and to allow automated Selenium tests to exercise the application's workflows”).
3.5 Web / Application Server — Apache Tomcat (backend) behind Nginx (frontend + reverse proxy)
What: The backend is packaged as a WAR and deployed to Apache Tomcat 10, the servlet container that hosts the running Spring Boot application, exactly as the brief's Week-8 task (“Deploy the build to Tomcat or Nginx”) specifies for a Java backend. An Nginx instance sits in front as the single public entry point: it serves the built React static files directly and reverse-proxies /api/ requests through to Tomcat.
Why: Tomcat is the standard, free, open-source servlet container for Java web applications and is what makes the Maven-built WAR runnable; it is also the deployment target the brief itself names. Nginx is added at the same layer to serve the frontend's static build efficiently and to give the deployment a single, well-known entry point for TLS termination and routing between the frontend and backend containers — satisfying the brief's “Tomcat or Nginx” deployment target with both tools used for what they are each best at, rather than treating the two as mutually exclusive alternatives.
3.6 Git and GitHub
What: Git for version control; GitHub for the shared remote repository, pull requests, code review, issue tracking, and — critically — as the webhook source that triggers Jenkins builds.
Why: Mandated by the Week 1/2 project brief; industry-standard; integrates natively with Jenkins via webhooks and with branch-protection rules that enforce the team's Definition of Done.
3.7 Jenkins
What: The CI/CD orchestration server. A declarative Jenkinsfile, checked into the repository, defines the pipeline stages (Section 5 and Section 14), invoking Maven (mvn clean package, mvn test) as its build job for the backend, per the brief's Week-7 task.
Why: Mandated by the project brief; free and self-hostable (a good fit for a student VM); its Jenkinsfile-as-code approach keeps the pipeline definition version-controlled alongside the application, and it has mature plugins for GitHub webhooks, Maven builds, JUnit-style test reporting, and Docker builds.
3.8 Selenium
What: Selenium WebDriver, used to drive an automated browser (headless Chrome) against a running instance of the application, exercising the MVP's core workflows end-to-end (login, create ticket, update status, search, dashboard view) for each role. Test cases are written as JUnit tests and executed through Maven (the Maven Surefire/Failsafe plugins), per the brief's Week-9 task (“Execute the suite locally through Maven”).
Why: Mandated by the project brief; the natural tool for functional UI testing of a web application, and directly enabled by the SRS's requirement that the API/UI separation be “sufficient to allow the automated Selenium tests ... to exercise the application's workflows” (§7.2).
3.9 Docker
What: Three containers — frontend (Nginx serving the built React app), backend (Tomcat with the Maven-built WAR deployed into its webapps folder), and database (MySQL, with a named volume for persistence) — orchestrated locally/in CI with Docker Compose.
Why: Mandated by the project brief; guarantees the application runs identically in development, in the Jenkins test stage, and in the deployment environment, and gives the team a clean, reproducible unit to hand to Ansible for deployment.
3.10 Configuration Management — Ansible (preferred over Puppet)
What: Ansible playbooks that provision the target host (install Docker/Docker Compose if absent), copy the deployment configuration, and bring the container stack up/down.
Why Ansible over Puppet: Ansible is agentless (it only needs SSH access to the target host, whereas Puppet requires an agent installed and a Puppet master server to be maintained) and uses simple, readable YAML playbooks rather than Puppet's declarative DSL. For a small student team managing a single target VM for demonstration purposes, Ansible's lower operational overhead — no master server to stand up and maintain — makes it the more manageable choice, while still meeting the project brief's “Ansible or Puppet” requirement.

4. High-Level Architecture
The application follows a conventional three-tier architecture: a browser-based presentation tier, a REST API tier containing business logic, and a relational persistence tier. All cross-tier communication is synchronous, over HTTP(S) and SQL respectively; no message queue or caching tier is introduced, since neither is required at MVP scale (NFR-06).

The Backend is the only tier permitted to query the Database. Each arrow represents a one-directional request; responses flow back along the same path.

4.1 Why a Monolithic Backend, Not Microservices
A single Spring Boot application, internally organised into modules (Section 6), was chosen over a microservices split (e.g., a separate authentication service, ticket service, and dashboard service). At MVP scale — a handful of related resources and a small team — microservices would add inter-service network calls, multiple deployable units, and multiple Docker images to build and orchestrate, without a corresponding benefit; the coherent, manageable stack this project calls for is better served by one deployable backend WAR with clearly separated internal packages/modules.

5.1 Component Explanations
Developer: Writes code locally, commits to a feature branch, and opens a pull request against the main branch, per the team's branching convention (Week 2).
GitHub: Hosts the canonical repository. Branch protection requires a passing pipeline before merge. A webhook on push/PR events triggers the Jenkins pipeline automatically.
Jenkins: Orchestrates all subsequent stages via a single Jenkinsfile checked into the repository, so the pipeline definition is versioned alongside the code it builds.
Build: Runs mvn clean package for the backend (Maven compiles, unit-tests, and packages the Spring Boot application as a deployable WAR — the brief's Maven build job) and npm ci / npm run build for the frontend (producing the React static bundle), as two parallel build artefacts.
Automated Tests: Runs backend unit/integration tests first via Maven (fast feedback), then spins up the application (e.g., via Docker Compose in a disposable CI environment, WAR deployed to Tomcat) and runs the Selenium suite — executed through Maven, per the brief's Week-9/10 tasks — against it to validate end-to-end role workflows.
Docker: Builds the frontend and backend images from their respective Dockerfiles once tests pass, tagging each image with the Git commit hash for traceability.
Registry: A container image registry (e.g., Docker Hub or the GitHub Container Registry) that stores tagged images, decoupling “where an image was built” from “where it is deployed from.”
Deployment: An Ansible playbook, invoked by Jenkins as the pipeline's final stage, connects to the target host over SSH, pulls the newly tagged images, and restarts the Docker Compose stack.
Application: The running set of containers (frontend, backend, database) that end users — Employees, IT Support Staff, and Administrators — access through a browser.

7.1 Authorization Enforcement Mechanism
Every authenticated request carries a JWT identifying the user's ID and role.
A Spring Security JWT filter decodes and validates the token before any controller method executes, rejecting requests with missing/expired/invalid tokens (SR-04).
A second Spring Security authorization layer (method-level @PreAuthorize checks and, where relevant, an explicit ownership check against assigned_to) checks the decoded role and ticket ownership against the permission matrix above before the request reaches business logic — so a direct API call attempting to bypass the UI is rejected identically to a disallowed UI action (SR-03).

11. Ticket Lifecycle Design
The ticket status lifecycle is fixed by the SRS (Section 3.3) and is treated here as an explicit, enforced state machine — the system must reject any transition not listed below, per the SRS business rule that “a ticket may only move between statuses along the transitions defined ... any other transition is invalid and shall be rejected.”
Diagram 4: Ticket Status State Machine
   [ Open ] ──(FR-08)──> [ Assigned ] ──(FR-09)──> [ In Progress ] ──(FR-10)──> [ Resolved ] ──(FR-11)──> [ Closed ]                   ^                                                                  |                   |__________________________ (FR-12, Administrator reassignment) ___|                                (any state → Assigned)
Components: Five states: Open, Assigned, In Progress, Resolved, Closed. One additional reassignment transition (FR-12) from any state back to Assigned.
Relationships / Arrows: Forward transitions are strictly sequential (Open→Assigned→In Progress→Resolved→Closed); the single exception is Administrator-initiated reassignment, which can occur from any state and returns the ticket to Assigned.
Explanation: No transition skips a state (e.g., Open directly to Closed is invalid), and no transition moves backward except via the explicit reassignment path — this matches the SRS business rule intent that the recorded workflow accurately reflect how a ticket was actually handled.

13. Deployment Architecture
The application is deployed as a fixed set of Docker containers on a single target host (a cloud VM or a local VM used for demonstration), consistent with SRS §2.4 (“a single server/virtual machine environment suitable for an academic deployment”).

                     Target Host (VM)        +---------------------------------------------+        |  Docker Compose stack                        |        |                                               |        |  +-----------+   +-----------+   +----------+ |        |  | frontend  |   | backend   |   | database | |        |  | (Nginx +  |-->| (Tomcat + |-->| (MySQL,  | |        |  | React     |   | Spring    |   | named    | |        |  | build)    |   | Boot WAR) |   | volume)  | |        |  | :80/:443  |   | :8080     |   | :3306    | |        |  +-----------+   +-----------+   +----------+ |        +---------------------------------------------+                       ^                       | HTTPS                 [ Browser / User ]
Components: One target host running Docker Compose with three containers: frontend (Nginx + built React app), backend (Apache Tomcat running the Maven-built Spring Boot WAR), database (MySQL with a persistent named volume). Deployment is managed by Ansible from the Jenkins pipeline.
Relationships / Arrows: Users reach only the frontend container's exposed port over HTTPS. The frontend container forwards API calls to the backend container over the internal Compose network. The backend container is the only one with access to the database container.
Explanation: Confining external access to a single exposed entry point (the frontend/Nginx container) and keeping the database container unreachable from outside the host's internal Docker network is a simple but meaningful security boundary, and it matches the single-VM deployment model the SRS operating environment describes.

15. Testing Architecture
Testing is layered, matching the pipeline stages in Section 14.
15.1 Unit / Integration Tests (Backend)
Scope: individual module methods (e.g., status-transition validation, search filtering logic) and Spring REST controller behaviour, run against a disposable test database (e.g., an in-memory H2 instance or a Dockerised MySQL test container).
Tooling: JUnit 5, with Spring Boot's test support (@SpringBootTest, MockMvc) for controller-level tests, run via Maven (mvn test) in the Jenkins Unit/Integration Tests stage — the Maven Surefire plugin produces the test report Jenkins publishes.
15.2 Where Selenium Fits
Selenium is the end-to-end, functional testing layer, sitting above the unit/integration layer. It does not replace backend unit tests; it validates the system the way a user actually experiences it — through the browser — which the SRS explicitly calls for (§7.2), and the official Week-3/9/10 task brief calls for specifically as a Maven-executed suite.
What it tests: complete role workflows driven through the rendered UI — e.g., an Employee logging in and creating a ticket (UC-01, UC-03); IT Support Staff taking up, progressing, and resolving a ticket (UC-06–UC-08); an Administrator reassigning a ticket and viewing the dashboard (UC-10, UC-11).
How it is run: Selenium WebDriver test cases are written as JUnit tests under the Maven integration-test source set and executed with the Maven Failsafe plugin (mvn verify), matching the brief's Week-9 instruction to “execute the suite locally through Maven” and Week-10's instruction to integrate that same suite into Jenkins.
When it runs: automatically, as its own stage in the Jenkins pipeline (Section 14), against a temporary Docker Compose instance of the full stack (WAR deployed to a Tomcat container) — never against the live demonstration deployment.
How it is structured: one Selenium test class/module per major workflow, using explicit waits (not fixed sleeps) for elements to render, and a dedicated seeded test dataset (test users for each role, a handful of sample tickets) that is reset before each run so tests are repeatable.
Why it matters for this project specifically: it is the automated proof that the frontend, backend, and database — three independently developed layers — genuinely work together, which is exactly the kind of regression a small team can otherwise miss.
16. Configuration Management Architecture
Ansible (selected over Puppet in Section 3.10) is responsible for taking a built, tested set of Docker images and turning them into a running application on the target host — the “Deployment” stage of Section 14.
16.1 Where Ansible Fits
Inventory: an Ansible inventory file lists the target host(s) — at minimum, the single demo/deployment VM; a staging host may be added later if the team's timeline allows.
Playbook responsibilities: (1) ensure Docker and Docker Compose are installed on the target host (idempotent — the playbook can be re-run safely without side effects if they are already present); (2) copy/update the Compose file and environment configuration (e.g., database credentials, JWT secret) onto the host; (3) log in to the container registry and pull the newly built image tags; (4) recreate the Compose stack with the new images; (5) verify the application responds (a basic health check).
Secrets handling: environment-specific values (database password, JWT signing secret) are kept out of the Git repository and supplied to Ansible via Ansible Vault or CI-injected environment variables, never hard-coded in the playbook.
Invocation: Jenkins runs the playbook (ansible-playbook deploy.yml) as the final pipeline stage over SSH, using a dedicated deployment key scoped only to that purpose.
This keeps deployment fully declarative and repeatable: the same playbook run against a freshly provisioned VM should produce the same running application, without any manual server configuration step.
17. Scalability and Maintainability Considerations
17.1 Scalability
The backend is stateless (session state lives in the JWT, not in server memory), so, if ever required beyond this project's scope, multiple backend container instances could be run behind a load balancer without code changes.
The database layer is the more likely bottleneck at higher load; indexes on frequently filtered/searched columns (status, category_id, created_by, assigned_to, and a full-text or LIKE-friendly index on title/description) keep the search and dashboard-aggregation queries efficient at the SRS's target scale of ~20–30 concurrent users (NFR-06).
No caching layer, message queue, or horizontal auto-scaling is introduced, since none is warranted at MVP/academic-demonstration scale; Section 19 records this as a deliberate limitation, not an oversight.
17.2 Maintainability
Categories and (if extended later) priorities are stored as database rows rather than hard-coded constants, so adding a category requires a data change, not a code change, directly satisfying NFR-05.
The module boundaries in Section 6 keep each functional area's logic together, so a change to, for example, search behaviour touches only the Search module and not the Status Workflow or Dashboard modules.
The Jenkinsfile and Ansible playbooks are version-controlled alongside the application code, so pipeline and infrastructure changes go through the same code-review process as application changes.

The official Week-3/7/9 task brief for this project mandates a Maven/Gradle/Ant build tool and a Tomcat/Nginx deployment target; a Node.js backend cannot satisfy that constraint. Java/Spring Boot is the most coherent, well-documented framework that builds with Maven and deploys as a WAR to Tomcat, while still exposing a clean REST API to the React frontend.
Maven build tool

Maven's declarative XML POM is more predictable for a small team new to Java tooling than Gradle's DSL, provides dependency management and a standard project layout Ant lacks, and integrates directly with Jenkins and with the Selenium suite as Maven test goals — see Section 3.2.1.
MySQL (relational)

Ticket/User/Category data is fixed-shape and relational, with meaningful foreign-key integrity requirements (e.g., a ticket must reference a real category); a relational database also makes the dashboard's grouped-count queries (FR-13/FR-14) simpler than they would be in a document model.
Monolithic backend
Microservices (separate auth/ticket/dashboard services)
Microservices would add inter-service network calls and multiple deployable units without a corresponding benefit at this scale, working against the brief's preference for a coherent, manageable stack.
REST API
GraphQL
REST requires no extra query-layer infrastructure, is simpler for Selenium/integration tests to exercise directly, and is sufficient for the MVP's small, well-defined set of resources.
Ansible for configuration management

Agentless (SSH-only, no master server to maintain) and lower operational overhead for a single target VM managed by a small team — see Section 3.10 for full justification.

Separate containers per tier match how the application is actually built and tested (frontend build vs backend runtime vs database), and allow each to be updated/scaled independently if ever needed.

19. Limitations of the Proposed Design
This design is intentionally scoped to an academic MVP running the Week 1/2/3 requirement set. The following limitations are acknowledged deliberately, not as oversights:
Single-host deployment: the design targets one VM running one Docker Compose stack; it does not provide high availability, automatic failover, or horizontal load balancing.
No caching or message-queue layer: acceptable at the SRS's target of ~20–30 concurrent users (NFR-06), but the design would need revisiting before any larger-scale or production use.
Academic-grade, not production-grade, security: SR-01–SR-05 are satisfied, but the design does not include rate limiting, intrusion detection, formal penetration testing, or a managed secrets vault beyond Ansible Vault.
No native mobile application: consistent with the Week 1 out-of-scope decision; the frontend is a desktop-browser web application only (SRS §7.4).
No self-registration: user accounts are provisioned by an Administrator only, consistent with the SRS's stated assumption (§2.6); there is no employee self-service signup flow.
Single-organisation, self-contained data model: no integration with external identity providers, email systems, or third-party ticketing tools, consistent with SRS §2.1.
Test environment fidelity: the Selenium suite runs against a temporary CI-built stack, not the live demo deployment, so a small class of purely environment-specific issues (e.g., host-level configuration drift) would not be caught by the pipeline alone.

Every module, database entity, API endpoint, and workflow rule in this design traces directly to a named SRS requirement or a specific line of the official task brief, so that implementation in the weeks that follow can proceed against a single, shared, unambiguous technical blueprint, without redefining scope already fixed by the Week 1, Week 2, and Week 3 deliverables.
No part of this architecture has been implemented at the time of writing; this document describes the plan against which implementation, testing, and the CI/CD pipeline itself will be built and evaluated in subsequent project weeks.
